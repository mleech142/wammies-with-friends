# Architecture

How Wammies With Friends is put together, the rules the code relies on, how it is tested, and where it could be made easier to maintain. For what the app does see the [README](../README.md); for how it compares with the spreadsheet see [excel-parity.md](excel-parity.md).

## Overview

A single-process Flask app serving four server-rendered pages, each driven by vanilla JavaScript that calls a JSON API. Game data comes from two places: the Wahapedia export the user downloads (read-only factions, units, weapons, points, detachments and enhancements from its datasheet files; stratagems, detachment and army rules with their text) and the app's own data JSON (custom units, rules and stratagems, edits to Wahapedia's, references). SQLite is a working copy of both, plus the user's saved armies, comparisons and games and the map of stable IDs. Before 3.0 the units came from BSData's catalogues; `carry_over.py` moved saved data to Wahapedia's IDs (docs/wahapedia-migration.md).

```text
 Wahapedia datasheet files ──(wahapedia_units.import_folder)───────────────────┐
   (user downloads into the wahapedia folder)                                  │
 Wahapedia export *.csv ──(wahapedia.import_folder; rules_text.parse_effects)───┤
   (user downloads into the wahapedia folder)                                   │
                                                                                ▼
 data/app_data.json ──────────────────────────────────────────────► data_store.merge_data ──► rebuild_reference_tables
   ▲ every confirmed Data-page edit (save_data → export_data → write_data_file)  (stable IDs)     (on every start)
   │                                                                                                  ▼
 Browser pages ──fetch──► Flask routes (routes/) ──► SQLAlchemy models (models.py) ──► data/combat_sim.db
   index / analytics /           │                                                   (reference tables, saved
   data                          ▼                                                    armies/comparisons, stable_ids)
                         simulation.py  (resolve → analytical / Monte Carlo)
```

## Data model: Wahapedia and the app data JSON

- **Wahapedia's units** (read-only): the export's datasheet files in the `wahapedia` folder, imported on every start by `wahapedia_units.py` (no cache: a second or two). No datasheet files yet is not an error (the app runs on its own data and the Simulator sends the host to Setup); an unreadable file is reported on the Setup and Data pages.
- **App data JSON** (`data/app_data.json`): custom factions with their units and weapons, all faction rules and stratagems, `unit_modifiers` added to downloaded units, keywords and target profiles. Record keys are the database column names, so loading and exporting are generic (`SECTIONS` in `data_store.py`). Rules and stratagems of a downloaded faction store its Wahapedia ID (`faction_key`) and name, not a database ID; added modifiers store the unit's datasheet ID and apply to that datasheet.
- **Reference vs persistent tables:** the tables in `REFERENCE_TABLES` are dropped and rebuilt on every start, so their schema can change freely. `saved_comparisons`, `saved_armies`, `saved_games` and `stable_ids` are *not* rebuilt (a database from before issue #25 also keeps an unused `saved_scenarios`): on start `create_all` adds missing tables and `models.add_missing_columns` adds new nullable columns; any other change needs a manual `ALTER TABLE`.
- **Write-through:** every data-editing route ends with `save_data()` (commit, then export the app's own records to the JSON). A new write route must call it.
- **Read-only:** downloaded factions' units and weapons (routes return 403; a downloaded unit only accepts `added_modifiers` and leader buffs), keywords and target profiles (no editing routes).
- **Stable IDs:** downloaded records get database IDs from `BSDATA_ID_BASE` up, recorded in `stable_ids` by key (`wh-unit:<datasheet>`, `wh-ranged:<faction>/<name>[@profile]` and so on: `wahapedia.stable_key` / `weapon_key`), so the same datasheet keeps its ID across downloads and saved armies and comparisons keep working. Custom records keep their own IDs, below the base (`next_custom_id`). A rule whose faction isn't loaded keeps a placeholder faction (`source` missing) with the same ID.
- **Weapons belong to a faction**; a unit's loadout links its own faction's weapons with a quantity (models carrying it) in datasheet order (`position`). Downloaded units also list wargear options, offered unticked on the Simulator and Analytics pages; an army entry sets how many models carry each (`loadouts.py`). A custom weapon can be copied from a downloaded weapon and stay linked to it (`linked_bsdata_id`, the weapon's `wahapedia.weapon_id`): its stats are refreshed on every start.
- **Leaders:** a leader's buffs (`leader_buffs`, rows like faction rules) are read from its abilities' text by `rules_text.parse_leader_buffs` and can be overridden in the app (`leader_buffs_override`, saved by datasheet ID). `/api/units/<id>` lists the leaders that can join a unit (`Unit.leaders()`, by the leaders' `can_lead` names); requests carry a `leader_id` and the server adds that leader's buffs to the attacking weapons or the target (`leader_modifiers`), and its points in Analytics. The leader's weapons are sent like the unit's own; resizing a unit never scales them. A defender with a leader is an **attached unit**: every attack goes to the bodyguard models until they are all destroyed, then to the leader, each stage with its own profile (Toughness, saves, wounds, Feel No Pain, keywords). The analytical engine (`simulate_attached_analytical`) spends each weapon's expected kills on the bodyguards and resolves the overflowing share of its attacks against the leader; Monte Carlo (`simulate_monte_carlo_attached`) rolls attack by attack and switches profile the moment the last bodyguard falls. Results carry `bodyguards_killed`, `leader_damage` and `leader_killed` (and `leader_kill_probability` in Monte Carlo). The pages show the leader as expected damage in analytical mode and as the chance it dies in Monte Carlo, never as analytical "kills". Matrix cells for an attached defender resolve the row's weapons in order; percentages count all its models. Reverse durability treats my units with leaders the same way. Precision and the "majority Toughness" rule are not modelled.
- **Detachments** come from the export with their rule text, Detachment Points cost and force dispositions (read-only; Boarding Actions ones are left out). Rules and stratagems can be limited to one (`detachment_key`, its Wahapedia ID, plus its name for when it isn't loaded); the Simulator and Analytics have a detachment checklist per side (`Core.detachmentPickerHtml`; several can be chosen), and `/api/rules/available?detachment=` (repeatable) offers faction-wide entries plus those of the chosen detachments. The Data tab shows each faction's army rules and detachment rules as reference text for writing rules and stratagems.
- **Wahapedia** (read-only text): the export in the `wahapedia` folder, imported on every start (no cache; it takes well under a second). Its stratagems and rules become `Stratagem` / `FactionRule` rows with `source` wahapedia, their `text` and `parse` (status, sentences not read, conditions dropped, and what was parsed), linked to the imported faction they belong to (`wahapedia.link`, by name and detachment) with stable IDs (`wahapedia:<kind>:<id>/<catalogue>`). Detachments or factions the datasheets don't have are listed as import notes. Only how the maths reads one (applies to, phase, modifier) can be edited, in every faction at once; edits are saved in the app data JSON's `wahapedia_overrides` by Wahapedia ID, and Reset goes back to the parsed values. Wahapedia's records are never written to the data JSON. The app data's own rules and stratagems that Wahapedia has too (same faction or core, same name) are `superseded`: hidden from the pages and ignored in saved ticks, but kept in the file. Stratagems used outside the Shooting and Fight phases (no phase) are listed on the Data tab but not offered on the pages; ticking a rule is the player saying its conditions hold, so the tick lists show the conditions that were dropped.

## Simulation engine

- **Excel parity is the contract.** `resolve()` mirrors the Sim sheets' helper columns: keywords and modifiers come from the weapon's abilities plus ticked attacker rules (attack side) and the target's keywords, modifiers, ticked target rules and extra modifiers (target side). Hit and wound modifiers are capped at ±1; BS/WS modifiers are not; cover worsens BS (11th edition); Lance/Cleave are melee-only, Heavy/Rapid Fire/Melta/cover/Stealth shooting-only.
- **Models killed** (analytical): each attack's damage is capped at the target's wounds; attacks per kill = ⌈W ÷ capped damage⌉ adjusted for Feel No Pain. A unit's weapons' kills add up, capped at the target's size; army totals add units' kills (uncapped, for "% destroyed").
- **Monte Carlo** rolls the same resolved rolls, caps each damage roll at W, and allocates damage model by model, giving exact kill and wipe chances. It rolls one attack at a time (`_roll_attack`), which is what lets an attached unit's target change mid-weapon.
- **Attached units** (leader + bodyguard): see *Leaders* above. The analytical engine's `leader_killed` is expected kills capped at the leader's models, as Excel does for units, so it overstates the leader's death when the bodyguards are only just wiped; the pages therefore show `leader_damage` instead (the two engines agree on it) and leave the chance of death to Monte Carlo.
- **Adding a keyword:** add it to `resolve()` (and both engines if it changes how rolls are made), add a case to `tests/test_simulation.py` and to the Monte Carlo agreement cases, and make sure the workbook's Keywords table (or `--reference-only` data) lists it.

## Conventions

- Say **"modifier"**, never "mod", in UI text and identifiers.
- Tests and harnesses must point `DATA_JSON`, `DATABASE_URL` and `WAHAPEDIA_DIR` at temporary copies (`tests/conftest.py` does this). Real Wahapedia files never go into the repository or the tests; `tests/fixtures/wahapedia` and `tests/fixtures/wahapedia_units` are made up (from `make_wahapedia_fixtures.py` next to them).
- Names from Wahapedia are imported exactly as written (Legends datasheets get " [Legends]"); likely problems are reported, not corrected.
- **Game rules live only in Python.** The pages get them from the server: `/api/units/<id>` sends each weapon's `default_use` and a `points_by_model_count` table, and `/api/keywords/check` checks keyword text. Don't re-implement a rule in JavaScript; add a field or endpoint instead.
- Pure page logic goes in `static/js/core.js` with a test in `tests/js/core.test.js`; the page scripts keep DOM and fetch code.

## Planned: Play mode

A Play page for full games between friends, on a top-down board, played live or asynchronously. It isn't built yet. The agreed design is in [play-mode-design.md](play-mode-design.md). Several decisions there affect the existing code:

- Game rules stay in Python. The board page asks the API about distances, line of sight and attack resolution.
- Game dice are separate from the engine: they use `simulation.resolve()` for what each roll needs, and the analytical and Monte Carlo functions stay unchanged and never use them. Attached units must work as in the simulator.
- Armies are frozen into each game by datasheet ID, never by database ID.
- Game state is plain JSON that doesn't depend on Flask, so it can later run under Pyodide.

## Maintainability review

### Fixed in this review

- **Scenarios page bug:** `GET /api/scenarios` was defined twice; the first, short version won, so the Scenarios page received no attacker/defender setup (names showed "Unknown" and loading a scenario lost its weapons). The duplicate is removed and a regression test added.
- **Dead endpoint:** `/api/weapons` (search weapons by unit) was no longer used by any page and has been removed.
- **Deprecated SQLAlchemy calls:** `Model.query.get()` / `get_or_404()` replaced with `db.session.get()` / `db.get_or_404()`.
- **Unused dependencies:** `pandas` and the Python `plotly` package removed from `requirements.txt` (charts use Plotly.js from a CDN); test tools moved to `requirements-dev.txt`.
- **Test gaps:** data editing, scenarios/comparisons and the migration script had little or no coverage (total was 65%); new test files bring it to 95%, and all API tests share one temporary-data fixture.
- **Duplicated rules removed and JavaScript tests added:** see *Duplicated logic* below and `tests/js`. Writing the tests found one more bug: resizing a unit restored from an older saved state drifted its weapon counts; fixed in `Core.scaleUnitSize`.

### Recommendations (not done)

In rough priority order:

1. ~~**Split `app.py` into blueprints**~~ Done (November 2026): `routes/`, one module per area, plain routes rather than blueprints so endpoint names stay. Was: (about 1,300 lines in one `register_routes` closure). Natural seams: `pages`, `data_api` (editing + export/import), `simulate` (Simulator + rules lists), `analytics` (matrix, cell detail, army analysis), `saved` (scenarios, comparisons). The helpers that close over `app` (`save_data`, `attacker_profile`, `defender_profile`) would move to a small service module.
2. **Move the Data page script out of the template.** `data.html` is about 1,350 lines, most of it inline JavaScript; a `static/js/data.js` would match the other pages and make it testable.
3. **Add a browser smoke test** (e.g. Playwright) for the main flows once a headless browser is reliably available; the Edge-based harnesses used during development were not kept.
4. **Split `style.css`** (about 2,700 lines) per page or component.
5. ~~**Split `play/game.py` into a package**~~ Not done, on purpose (November 2026). Measured, its sections (setup, movement, shooting, reactions, charges, fight, transports, reserves, terrain) call each other in both directions almost everywhere, so separate files would mean import cycles without a simpler design. Instead its interface is explicit: `__all__` lists what the rest of the app may use (playing a game: `new_game`, `resolve_action`, `apply_event`, `apply_in_place`, `replay`, `redo_history`; and what the board shows and offers now), and `tests/test_play_interface.py` fails if another module reaches past it. `play/mission_state.py` and `play/tactical.py` are part of the engine and share its private helpers. `apply_in_place` (was `_apply`) is the session cache's way to replay only new moves.
6. **Hosted mode makes 1 more pressing:** with routes split by area, each feature's checks (sizes, who may do it) sit with its routes.

Fixed in the same review: request size limit, safety headers, JSON answers for every API error, model counts capped at 99 and a Monte Carlo roll budget (`simulation.affordable_trials`: one request's Python holds up every other request), the game list without each game's moves, and capped Docker logs and nightly backups for a self-hosted copy (`scripts/backup.sh`).

### Duplicated logic (resolved)

Earlier versions implemented these rules in both Python and JavaScript (and the points rounding once disagreed). Each now has a single Python implementation that the pages use through the API:

| Rule | Implementation | How the pages get it |
| --- | --- | --- |
| Default weapon ticks (only the first "Weapon - Profile" variant) | `app.default_used` | `default_use` on each weapon from `/api/units/<id>` (and used directly for reverse durability) |
| Points for a unit size (brackets, round half up) | `Unit.points_for` | `points_by_model_count` table from `/api/units/<id>`; the matrix also returns points |
| Keyword parsing and checking | `simulation.keyword_name` / `check_keywords` (also used by the units importer's report) | `POST /api/keywords/check` (KeywordHints) |
