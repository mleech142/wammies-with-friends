# Wammies With Friends

Called 40K Combat Simulator before 2.9: the code keeps that name inside (the `combat_sim` package, `COMBAT_SIM_*` settings, the `combat-sim-game` file format, the Docker service and volume); only what people see is Wammies With Friends.

Flask app in `src/combat_sim/`. Entry point: `python run.py` (waitress on 127.0.0.1:5000, or a free port; `--debug` for Flask's debugger — never ship debug on).

**Terminology:** always write "modifier", never "mod", in UI text and code identifiers (e.g. `extra_modifiers`, "Extra modifiers").

## Data

Two sources, merged into the reference tables on every start and on every download by `reference.load` (`data_store.merge_data` → `rebuild_reference_tables`, one transaction; what was loaded is published as one snapshot, `reference.current(app)`, never as loose `app.config` keys):

- **Wahapedia export** ([data export](https://wahapedia.ru/wh40k11ed/the-rules/data-export)): factions, units, weapons, loadouts, points, detachments and enhancements (its datasheet files), and stratagems, detachment rules and army rules, word for word. Users download it on the Setup page (`/setup`, "Download latest": `wahapedia_download.py`, the files in `wahapedia_download.DOWNLOAD_FILES` into the `wahapedia` folder next to the app data JSON, or `WAHAPEDIA_DIR`). **Never commit or ship it** (`data/wahapedia/` is gitignored), and keep the "powered by Wahapedia" credit. `src/combat_sim/wahapedia_units.py` imports the datasheet files (no cache), `src/combat_sim/wahapedia.py` the rules and stratagems, matched to the imported factions by detachment and faction name; `rules_text.parse_effects` reads each record's text into one side / phase / modifier. Rules and stratagems are `Stratagem` / `FactionRule` rows with `source` wahapedia: read-only (DELETE returns 403) except how the maths reads them, saved as `wahapedia_overrides` by Wahapedia ID. The app data's rules and stratagems with the same faction and name are `superseded` (hidden, kept in the file). Its text is HTML, turned into the app's markup (`**bold**`, `^^keyword^^`, bullets) by `wahapedia.markup`: keep the markup in stored text, parse with `rules_text.plain_text`, render with `Core.formatRuleText` (never insert it as raw HTML).
- **Before 3.0 units came from BSData** (BSData/wh40k-11e, taken down in 2026). `carry_over.py` moves data saved then to Wahapedia's IDs through the shipped `data/bsdata_id_map.json` (made once by `scripts/make_bsdata_id_map.py`; it holds IDs only): on the first start with the export (`reference._carry_over`) it re-keys `stable_ids` (merged copies remapped to the lowest ID), rewrites saved armies (unmatched units kept with `missing`, their old name), comparisons, games and proposals, upgrades the app data JSON from `schema_version` 2 to 3 and writes `carry_over_report.json` (shown to the host on the Setup page); version 1 share codes are translated by `carry_over.share_payload`. Design and status: `docs/wahapedia-migration.md`. Column and field names (`bsdata_id`, `source` 'bsdata', `linked_bsdata_id`, `bsdata_result`) are kept from then and hold Wahapedia's IDs.
- **App data JSON** (`data/app_data.json`, committed and shipped): everything the app owns — custom factions with their units and weapons, faction rules and stratagems, modifiers added to downloaded units (`unit_modifiers`), the keyword glossary and target profiles. Format and loading live in `src/combat_sim/data_store.py` (`schema_version` 3, record keys = DB column names; version 1 files load as all-custom data, version 2 is BSData's IDs, upgraded by the carry-over).

Rules:

- Downloaded factions' units and weapons are **read-only** (the routes return 403); their hand-written rules, stratagems and added modifiers are app data.
- **Detachments** (and factions' army rules) come from the export (`Detachment` table, `/api/detachments`): rule text, Detachment Points cost (`dp`) and force dispositions (`wahapedia_units.FORCE_DISPOSITIONS`); Boarding Actions detachments and their enhancements are left out, and the export has no Unique Tags. A side or army can choose several. A rule or stratagem with a `detachment_key` (the detachment's Wahapedia ID) is offered by `/api/rules/available` only when that detachment is chosen (`?detachment=`, repeatable); ticking still decides what applies.
- **Enhancements** come from the export (`Enhancement` table, `/api/enhancements`): points, text, `buffs` (`rules_text.parse_enhancement`, each for the bearer or its unit), and the datasheets that can take one (`bearer_bsdata_ids`, from `Datasheets_enhancements`; an Upgrade for one datasheet is its `unit_bsdata_id`), checked by `armies.enhancement_allowed` (never Epic Heroes). Requests carry a unit's enhancements as `enhancements: [{id, bearer: 'unit'|'leader'}]` (and each matrix weapon whether it is the `leader`'s); the server adds their effects and points (`engagement.py`).
- **Wargear** is simple (`loadouts.py`): a unit's weapons are its datasheet loadout (scaled to its size) plus its options (`ranged_options` / `melee_options`, and the datasheet's option text, `Unit.wargear_options`). An army entry's `wargear` is how many models carry each weapon, `{'ranged:<id>': n, 'melee:<id>': n, 'wargear:<name key>': n}` (None: the datasheet's); the Armies page's Wargear popup (`POST /api/armies/wargear`) sets the counts beside the option text. There are no limits. The datasheet's "per X" costs (`Unit.wargear_costs`) price it: a cost naming one of the unit's weapons is paid for each one beyond the datasheet's loadout, any other (a storm shield) is a count of its own (`wargear:`); `price_army` adds them to the unit's points (`wargear_points`). `price_army` turns the counts into `loadout` rows, which Analytics (the roster's `loadout` / `leader_loadout`), Match view and Play read. Share codes carry them by the weapons' stable keys. A unit's characteristics are read only by `engagement.unit_stats`.
- **Rule text** is read in `rules_text.py`: `parse_leader_buffs` (leaders), `parse_effects` (stratagems, detachment and army rules) and `parse_enhancement` share one sentence parser; extend it there, with a case in `tests/test_wahapedia.py`.
- **Leaders:** who leads or supports whom comes from the export's `Datasheets_leader`; `Unit.leader_buffs` (rows like faction rules: applies_to / phase / modifier) are parsed from the leader's abilities by `rules_text.parse_leader_buffs`; an edit in the app is `leader_buffs_override` (app data `leader_buffs`, by datasheet ID). Requests name a unit's leader with `leader_id` (`/api/simulate` attacker/defender, matrix attackers/defenders/weapons, cell detail) and the server applies its buffs (`engagement.py`); the pages add the leader's weapons (`Core.withLeaderWeapons` / `withLeaderEntries`). A defender (or, in reverse durability, my unit) with a leader is an attached unit: `simulate_attached_analytical` / `simulate_monte_carlo_attached` send attacks at the bodyguard models, then the leader (`engagement.leader_target`), each stage with its own profile; results carry `bodyguards_killed`, `leader_damage` and `leader_killed`; pages show the leader as expected damage (analytical) or chance it dies (Monte Carlo), not as analytical kills. Any new engine feature must work for attached targets too.
- A custom weapon with `linked_bsdata_id` (a downloaded weapon's `wahapedia.weapon_id`, e.g. `SF/heavylaser`) takes its stats from that weapon on every start (`data_store.LINKED_FIELDS`); its name and faction are its own. Units and weapons can only be created in custom factions (`Faction.source == 'custom'`).
- App data refers to downloaded records by Wahapedia ID (`faction_key` = faction ID, `unit_modifiers[].bsdata_id` = datasheet ID), never by database ID. Downloaded records get database IDs from `BSDATA_ID_BASE` (1,000,000) up via the persistent `stable_ids` table, keyed `wh-unit:<id>`, `wh-ranged:<faction>/<name>[@profile]` and so on (`wahapedia.stable_key` / `weapon_key`), so saved armies and comparisons survive downloads; custom records keep IDs below it (`next_custom_id`).
- Reference tables are dropped and rebuilt on every start, so their schema changes need no DB migration. Saved comparisons, armies, games and `stable_ids` are *not* rebuilt: new tables and new nullable columns are added on start (`models.add_missing_columns`); anything else still needs a manual `ALTER TABLE`.
- Every change to the shared app data is an edit made by `app_data_edits.py` (`apply(app, edit)` makes it, saves and rewrites the app data JSON; `preview(edit)` makes it and undoes it to say what it changes; `EditError` for one that can't be made). Data-tab write routes live under `/api/data/`, are labelled `@edit_route(kind, action)` and only call `run_edit(edits.make(...))`; on a self-hosted copy a player's becomes a proposal holding the edit (`proposals.py`), checked when proposed and applied the same way when the host approves.
- Tests/harnesses must set `DATA_JSON` and `DATABASE_URL` (and `WAHAPEDIA_DIR`) to scratch copies, or edits will overwrite the real files. With `DATA_JSON` set, the Wahapedia folder defaults to its folder, never the repo's.

**Weapons belong to a faction** (`faction_id`). A unit's loadout is the `unit_ranged_weapons` / `unit_melee_weapons` link tables with a `qty` = models in the unit carrying that weapon and a `position` (datasheet order); read it with `Unit.loadout(type)`, write with `Unit.set_loadout(type, entries)` (the relationships are view-only). Downloaded units also list wargear options (`ranged_options` / `melee_options`), which the Simulator and Analytics show unticked under the loadout (`Core.simulatorWeapons` / `Core.matchupWeapons`). Matchup attackers carry the attacking `unit_id` alongside `weapon_id`.

## Packaging and releases

Users get a Windows or Linux build made by PyInstaller (`combat_sim.spec`, the same spec for both) and published by `.github/workflows/release.yml` when a `vX.Y.Z` tag matching `__version__` in `src/combat_sim/__init__.py` is pushed: each platform is tested and built on its own runner (Linux on Ubuntu 22.04 for older glibc), and the release is published only when both succeed (*Run workflow* builds both without publishing). `.github/workflows/tests.yml` runs the tests on Linux for every push; keep the code platform-neutral (no Windows-only paths or calls). In a build, data lives in `%APPDATA%\Wammies With Friends\` on Windows and `~/.local/share/Wammies With Friends/` on Linux (`src/combat_sim/paths.py`; the first start of 2.9 renames a `40K Combat Simulator` folder, `paths.move_old_folder`); the shipped app data JSON only seeds it on first run (except its keyword glossary: entries the user's copy lacks are added on every load, `data_store.with_shipped_keywords`; harnesses with their own `DATA_JSON` get none unless they set `SHIPPED_DATA_JSON`), and a version 1 `40k_data.json` and database found there are moved to `archive-v1`. **Self-hosting** (release 2.8, steps a to d built; plan and decisions: `docs/hosted-version-scope.md` sections 7 and 8, agreed with the owner; phone layouts after it: see **Phones** below): a Docker image (`Dockerfile`, `compose.yaml`) that `release.yml` pushes to ghcr.io with each release, running `run.py --hosted` with its data in `COMBAT_SIM_DATA` (`docs/self-hosting.md`). In hosted mode (`app.config['HOSTED']`) other people's browsers reach the app: anything that only makes sense on your own PC (paths on the server, the relay address) is refused with 403, and never ship the image with Wahapedia files. Hosted mode has named players (`accounts.py`: logins, join links, the Players page). **Who may do what is decided only in `access.py`**: every route is for any logged-in player unless labelled just under its `@app.route` with `@open_to_all`, `@host_only`, `@proposable` (Data-tab writes: a player's becomes a proposal) or `@desktop_only`, and the app refuses to start with an unlabelled Data-tab write route. Saved records carry `owner_id` (None: the host's) and a sharing rule in `access.POLICY` (armies shared read-only, games their two players, proposals their author and the host, the rest private; a new saved table with an owner must be added, or the app won't start); routes read and change them only through `access.get(Model, id[, write=True])`, `access.listed` / `access.visible` / `access.mine` and `access.stamp()`, never by checking hosted mode themselves. Who is acting is `access.principal()`: a `Desktop` (a desktop install: its own host, owning everything, `local`), a `Player` or a `Visitor` (not logged in); routes and pages ask it (`is_host`, `shared`: the copy has several players, `local`: paths on this computer allowed) instead of `HOSTED`. Settings are the install's (`settings.json`, the host's: downloads, relay) or a person's own preferences (`settings.PREFERENCES`: Play in the menu, online name), read and changed only through `principal().preferences()` / `set_preferences()` (a player's are in their account, falling back to the install's). Which side a player plays in a game is its connection's (`play/connections.py`). Tests: `tests/test_access.py`. Anything new the pages load must be bundled locally (no CDNs; icons are Font Awesome Free solid from `static/vendor/fontawesome-free-7.3.1`, written `<i class="fa-solid fa-NAME" aria-hidden="true"></i>`, and `tests/test_packaging.py` checks every one exists) and anything new on disk must be added to the spec's `datas`. Steps: `docs/releasing.md`.

## Excel Source

The v2 workbook `40KCombatSimulator_v2.xlsx` is frozen; it is now only the simulation engine's parity reference. The v1 data JSON, its database and the old `migrate_excel.py` are in `archive/`.

## Simulation engine

**Every attack's modifier text is assembled by `engagement.py`** (`attack_modifiers` / `target_modifiers` from one side's `Sources`: ticked rules, leader buffs, enhancements, datasheet abilities, Death Guard, one-off modifiers) for the Simulator, Analytics (matrix, cell detail, reverse durability) and Play; a new source of effects goes there. `src/combat_sim/simulation.py` mirrors the v2 sheet's formulas: `resolve()` turns a weapon (abilities + type) and target (keywords/modifiers) into rolls needed, then the analytical and Monte Carlo engines both consume it. Any new keyword must go in `resolve()` and be covered by both engines. A route that runs Monte Carlo takes its trial count from `simulation.affordable_trials` (a budget of attacks rolled per request: one request's Python holds up every other request on a shared server), and model counts from requests go through `engagement.clamp_models`. Tests: `python -m pytest tests` (includes Excel's own cached results as parity fixtures and an analytical/Monte Carlo agreement check). Feature-by-feature status against the workbook: `docs/excel-parity.md`.

## Routes

- `/` - Single combat simulator
- `/analytics` - Attacker units × defender units matrix + Army Analysis
- `/play` - Play mode (experimental; in the menu only when ticked on the Setup page): games between two saved armies on a top-down board. Code in `src/combat_sim/play/` (routes in `play/routes.py`); games are `SavedGame` rows (database only). Design and status: `docs/play-mode-design.md`; what's next: its Roadmap (Next) and the owner's testing list, `docs/testing-list.md` (items are noted there and not started until the owner picks them)
  - **The rules engine** is `play/game.py` with `play/mission_state.py` and `play/tactical.py`; the rest of the app uses only what `play/game.py`'s `__all__` lists (`tests/test_play_interface.py`). Add to it rather than importing a private helper.
  - **Changing a game** goes only through `play/session.py`'s `GameSession` (`act`, `undo`, `sync`, `state`: saves only if the game is unchanged since it was read, keeps recent states in a cache), and what differs between hot-seat, game-file, relay and same-copy games is only in `play/connections.py` (one adapter per kind, `kind_of` works it out from the stored fields; the relay is a port, `app.config['RELAY']`, tests use `tests/memory_relay.py`). Routes turn requests into session calls; what the board draws from is `play/view.py`'s `board()` (including which stratagems are usable now and VP against the caps: the page never works out a game rule itself). Tests: `tests/test_play_view.py`. Tests: `tests/test_play_session.py`; the tests check every cached state against a full replay (`PLAY_STATE_CHECK`).
  - **The game screen** (Play UI/UX, `docs/play-mode-design.md`): a game open makes the page the game (`body.play-game-mode`: the board fills the window, the selected unit's actions in a bar under it, the log a drawer; phones a full-screen game screen). Previews come from the server: `POST /api/play/games/<id>/preview` (`game.attack_preview`: models likely killed and the chances, rolled with the Simulator's dice, never game dice), `charge_options`' `reach` (`game.charge_chance`), and `POST .../check` (`GameSession.check`: a dry run of a dragged move). The page never works out these odds itself.
  - **Battle mats** (the picture under the board): `static/img/mats`, listed in `Core.PLAY_MATS`, one per game from its ID, shown at `Core.PLAY_MAT_STRENGTH` (35%). Seven so far (Hive Sector, Red Planet, Ruined Highway, Ash Wastes, Death World Jungle, Forge Yard, Tomb World), drawn by the prototype; **the owner will replace them with improved versions** (refined outside the app) and may add more. Format, rules and plan: `docs/play-mode-design.md`, Battle mats. Never add Games Workshop art (emblems such as the aquila included).
- `/armies` - Army lists: build, save, copy, export as text, share as a code another install imports (`army_share.py`: Wahapedia IDs only, wargear included; lists with custom units are refused), send to Analytics (`/analytics?army=<id>&side=attacker|defender`). Pricing and checks are in `armies.py` (`POST /api/armies/price` on every change): points, detachments' DP and Unique Tags, copies of a datasheet (the core rule), leaders and support units (`Unit.can_support`), the Warlord and enhancements. Lists are `SavedArmy` rows (database only, not the app data JSON)
- `/armies/<id>/match` - Match view of a saved army (the Armies page's **Match view** button saves first): every unit's datasheet at its size and wargear, its leaders, the army and detachment rules, enhancements taken and the stratagems it can use, filtered by phase and turn; printable. Data from `match_view.py`, drawn by `static/js/match.js`
- `/setup` - Download Wahapedia's export (units, rules and stratagems); import notes; what the carry-over from BSData changed (host only). Downloads run as jobs (`jobs.py`: `of(app).submit(kind, work)`, one of a kind at a time; the route answers 202 with the job, the page polls `/api/jobs/<id>`), as do "your move" emails; long new work goes there, never in the request. Tests run jobs inline (`app.config['JOBS'] = 'inline'`, set by `make_client`). `/` redirects here until the units load or setup is skipped
- `/data` - Import status; factions (with rules and stratagems), units and weapons (downloaded read-only, custom editable); read-only Keywords and Target Profiles

API routes are in `src/combat_sim/routes/`, one module per area (simulator, catalogue, analytics, army_lists, saved, data_tab, setup), each with `register(app)`: plain routes, not blueprints, so endpoint names stay as `access.py` labels them; `app.py` only has `create_app()`. `static/js/app.js` is loaded on every page (shared `PageState`, `KeywordHints`). `/api/units` and `/api/data/units` leave Legends units out unless `?legends=1`.

## Phones

Every page works on a phone (360px wide and up) and by touch (`docs/phone-plan.md`, its section 7 lists what is where). Phone layout goes behind `@media (max-width: 900px)` / `(max-width: 600px)` and touch sizing behind `(pointer: coarse)` (in JavaScript, `event.pointerType === 'touch'`), so desktop pages and mouse controls stay as they are. Which layout a device gets is also worked out once, from what it can do (never its user-agent string): `base.html` sets `data-layout` (`phone`, `tablet` or `desktop`) on `<html>` before the page draws, by `Core.layoutFor` (the screen's short side under 600px with touch and no hover is a phone, held either way) or the person's Layout preference (`settings.PREFERENCES` `layout`, set on the Setup, Account and Play pages through `select[data-layout-setting]`); `window.applyLayout()` works it out again and a change fires `layout-changed`. Play's game screen keys off `[data-layout="phone"]` (a phone held sideways is wider than 600px); other pages keep the width queries. Use the shared pieces at the end of `style.css` and in `app.js` rather than new ones: tables as `.table-scroll.sticky-first` (number grids) or `table.cards-on-phone` with `data-auto-labels` (lists), full-screen pop-ups, and `Core.infoButton(text)` for anything a player needs to read that would otherwise be a hover-only `title`. On every page: font sizes, corners and spacing are the tokens at the top of `style.css` (`--fs-*`, `--radius-*`, `--space-*`; no new raw sizes), titles use `--font-display` (Barlow Condensed, bundled in `static/vendor`), the accent marks only the one primary action and what is selected, empty states use `.empty-state`, feedback uses `Toast.show(text[, 'error'])` (not `alert`), slow buttons `Busy.during(button, promise)`, desktop menus `.dropdown` (`Dropdowns` in `app.js`), and a page's main actions carry `data-command="..."` so the Ctrl+K command palette (`CommandPalette`) offers them. Up to 900px the main pages are a tab bar at the bottom (`base.html`; the rest under More, the header's links as a sheet) and the header shows the page's name. Every `title` is also a tip (`Tips` in `app.js`): a tap or click on plain text, a long-press on a button, as a sheet with its name on a phone; weapon abilities are chips explaining themselves (`AbilityHints`, from `ability_hints` on `/api/units/<id>`). A page's main action goes in an `.action-bar` (fixed above the tabs on phones), less-used buttons in an `.overflow` group (an action sheet on phones, in place on wider screens), long notes get `data-read-more`, a `<select data-segmented>` shows as buttons, and `Sheets` (grip, drag down to close), `Toast` and `Haptics` are shared. Anything done with a modifier key, a key, the mouse wheel or hover also needs a button or a gesture. `tests/test_phone.py` (and `test_phone_hosted.py` for a self-hosted copy's pages) opens every page and its main states at 360px with touch and fails on sideways scrolling, tap targets under 44px (ticks 24px) or field text under 16px: add a new page or pop-up to its `PAGES`. `PHONE_REPORT=1 PHONE_SHOTS=<folder> python -m pytest tests/test_phone.py -s -k report` prints what each page still has to fix and saves screenshots.

## Testing

`pip install -r requirements-dev.txt` and `python -m playwright install chromium` (the phone checks; Chrome or Edge already installed also work), then `python -m pytest tests` (also runs the Node tests in `tests/js` via `test_javascript.py`). API tests use the `make_client(data, wahapedia=None)` fixture in `tests/conftest.py`, which runs the app on a temporary data JSON and database — use it for any new API test. Pass `wahapedia=WAHAPEDIA_FIXTURES` for the made-up export in `tests/fixtures/wahapedia` (units, rules and stratagems) or `wahapedia=UNIT_FIXTURES` for its units alone (`tests/fixtures/wahapedia_units`, without `Stratagems.csv`); regenerate both with `tests/fixtures/make_wahapedia_fixtures.py`, and never put real Wahapedia files in tests.

**Game rules live only in Python.** Pages get them via the API (`default_use` and `points_by_model_count` on `/api/units/<id>`, `POST /api/keywords/check`, the Wargear popup's counts); never re-implement them in JavaScript. Pure page logic belongs in `static/js/core.js` (loaded first on every page, `require()`-able in Node) with tests in `tests/js/core.test.js`.

Module map, invariants, coverage and the maintainability backlog: `docs/architecture.md`.

**Play mode (planned, not built):** full games between friends on a top-down board, live or asynchronous. The agreed design and roadmap are in `docs/play-mode-design.md`; read it before any Play-mode work and don't reopen its settled decisions without asking. Game dice live in the `play` package and only share `simulation.resolve()`; never change the analytical or Monte Carlo functions for the game, and never use game dice in the Simulator or Analytics. The Event Companion's terrain layouts are data in `play/layouts.py`, written from Games Workshop's free PDF by `scripts/extract_event_layouts.py` (never commit the PDF).
